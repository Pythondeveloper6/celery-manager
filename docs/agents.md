# Building with AI agents

celery-manager gives agents three things: a **Model Context Protocol (MCP)
server** that lets them look at and, if you allow it, operate your Celery
system; **machine-readable docs** (`llms.txt`) so a coding agent can wire the
package into your project correctly; and **LLM-usage tracking** for the agent
workloads your tasks run ([LLM usage](llm-usage.md)).

## The MCP server

```bash
celery-manager mcp --app myproject.celery:app --db-url postgresql+psycopg://... --role viewer
```

It speaks MCP over stdio (newline-delimited JSON-RPC) and needs no extra
dependency. Register it with any MCP client, for example:

```json
{
  "mcpServers": {
    "celery-manager": {
      "command": "celery-manager",
      "args": ["mcp", "--app", "myproject.celery:app", "--db-url", "postgresql+psycopg://...",
               "--role", "viewer", "--agent-name", "triage-bot"]
    }
  }
}
```

`--config module:attr` works too, for settings with no flag (`environment_name`,
`operator_safeguards`, `llm_prices`, SMTP). The server runs next to your
database, like the other CLI commands, and shares nothing with a running
dashboard.

### Roles decide what the agent can do

The agent acts as one fixed principal, `mcp:<agent-name>`, at the role you pass
to `--role`. Tools above that role are **not listed and cannot be called**.

| Role | Adds |
|---|---|
| `viewer` (default) | Read-only: runs, failure groups, workers, queues, schedules, alerts, LLM usage, `run_doctor` |
| `operator` | `retry_run`, `retry_runs`, `cancel_run`, `start_task`, `pause_schedule`, `resume_schedule`, `set_rate_limit`, `acknowledge_dead_letter` |
| `admin` | `preview_queue_purge`, `purge_queue` |

Start with `viewer`. Every tool calls the same REST route the dashboard uses, so
validation, role checks, [operator safeguards](configuration.md) and the
[audit log](rest-api.md#audit-log) behave exactly as for a person. Audit rows
show the actor as `mcp:<agent-name>`.

### Guard rails built into the tools

- `retry_runs` defaults to `dry_run=true`. A real bulk retry needs
  `dry_run=false` and `confirm_count` equal to the number of ids (max 500).
- `purge_queue` needs `confirm` equal to the queue name.
- Write tools accept a `reason`. It is sent as the `X-CM-Action-Reason` header,
  so `operator_safeguards` deployments accept it, and it lands in the audit
  details.
- Arguments are checked against each tool's schema before any call; unknown or
  mistyped arguments come back as an error naming the field.
- Results over 40,000 characters are cut with a note to narrow the filters.

### Treat task data as untrusted

Task arguments, exceptions, tracebacks, logs and results come from your
application and can contain text written by outsiders. The server says so in its
instructions and in each tool's description, but the safest setup is also the
simplest: give an agent the `viewer` role unless it needs to act, and review
what an `operator` agent does through the audit log.

### Tools

| Tool | Role | What it returns |
|---|---|---|
| `list_runs`, `get_run`, `get_related_runs`, `get_workflow` | viewer | Run history and detail |
| `failure_groups`, `analytics_overview`, `task_stats` | viewer | Where things are failing, success rate, runtimes |
| `llm_usage`, `run_llm_usage` | viewer | LLM calls, tokens, cost |
| `list_dead_letters` | viewer | Runs that exhausted retries |
| `list_workers`, `list_rate_limits` | viewer | Live worker state, rate limits |
| `list_queues`, `queue_history`, `broker_health` | viewer | Depth, history, broker state |
| `list_schedules`, `schedule_health`, `beat_health` | viewer | Periodic schedules and whether they fire |
| `list_alert_incidents`, `list_alert_rules` | viewer | Alerting state |
| `list_registered_tasks`, `whoami`, `run_doctor` | viewer | Task names and signatures, identity, preflight |

## Machine-readable docs

- [`llms.txt`](llms.txt) is a short index of the documentation for agents.
- [`llms-full.txt`](llms-full.txt) is the whole documentation in one file, for
  loading into a coding agent's context. It is generated by
  `python scripts/build_llms_txt.py` and checked in CI.
- `celery-manager openapi -o openapi.json` writes the REST API's OpenAPI
  document offline, for generating a typed client.
- `celery-manager doctor --json` prints the preflight as JSON (`ok` and a list
  of checks with `name`, `state` and `detail`); `--fix-suggestions` prints a
  Markdown checklist with a fix for each open item.

### Teach your own coding agent

Paste this into your project's `AGENTS.md` or `CLAUDE.md` so an agent that edits
your code uses celery-manager correctly:

```markdown
## celery-manager
- Docs for agents: https://pythondeveloper6.github.io/celery-manager/llms-full.txt
- Call `celery_manager.setup(config)` once per process, including the Celery worker.
- Decorate tasks with `@app.task` first, then `@track()` directly below it.
- Record LLM calls inside tasks with `record_llm_usage(response=...)`.
- Run `celery-manager doctor --fix-suggestions` after changing Celery settings.
```

## Not included

Authenticated remote access (an HTTP transport with API tokens) is not part of
this release: the MCP server runs where the database is. Idempotency keys on
write routes are not implemented either; the bulk tools' dry run and
confirmation counts are the protection against repeated calls.
