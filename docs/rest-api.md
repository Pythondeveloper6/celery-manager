# REST API reference

Every endpoint below is served under `/api` by the FastAPI app returned
from `celery_manager.api.app.create_app()`. This page documents actual
current behavior, generated by hand from the route files
(`src/celery_manager/api/routes/*.py`) — several endpoints evolved during
implementation, so treat this as the source of truth over any earlier
design notes.

## Auth

All auth is cookie-based: `POST /api/auth/login` sets an `httponly`,
`samesite=lax` session cookie (signed with `CeleryManagerConfig.secret_key`
via `itsdangerous`, valid 7 days); every other endpoint below except login
reads that cookie via the `get_current_user` dependency and returns
**`401`** if it's missing, invalid, or expired. There are no API keys,
bearer tokens, or scopes — one authenticated user can do everything.

| Method | Path | Auth | Request body | Response |
|---|---|---|---|---|
| `POST` | `/api/auth/login` | none | `{"username": str, "password": str}` | `200 {"username": str}` on success; `401 {"detail": "invalid credentials"}` on bad username/password. Sets the `session` cookie. |
| `POST` | `/api/auth/logout` | none | — | `200 {"ok": true}`. Deletes the `session` cookie (no server-side session store to invalidate — the cookie itself is the only state). |
| `GET` | `/api/whoami` | required | — | `200 {"username": str}` if authenticated; `401` otherwise. This is what the dashboard SPA calls on load to decide whether to show the login screen. |

## Tasks

| Method | Path | Auth | Request | Response |
|---|---|---|---|---|
| `GET` | `/api/tasks` | required | Query params: `status` (optional, e.g. `queued`/`started`/`succeeded`/`failed`/`retried`/`skipped`/`revoked`), `task_name` (optional, exact match). No pagination params exposed at the route (the underlying `list_task_runs` supports `limit`/`offset`, defaulting to `limit=50, offset=0`, but the route doesn't currently forward them from the query string). | `200` — list of `{"task_id", "task_name", "status", "started_at", "finished_at"}`, newest first (ordered by internal row id descending). |
| `GET` | `/api/tasks/{task_id}` | required | — | `200` — `{"task_id", "task_name", "status", "args", "kwargs", "exception", "traceback", "log_output"}` (`args`/`kwargs` are JSON-encoded strings, not parsed objects). `404 {"detail": "not found"}` if no run with that `task_id` exists. |
| `POST` | `/api/tasks/start` | required | `{"task_name": str, "args": [...] = [], "kwargs": {...} = {}}` | `200 {"task_id": str}`. Dispatches immediately via `celery_app.send_task(...)` — no validation that `task_name` is a registered task; a bad name fails at the broker/worker level, not here. |
| `POST` | `/api/tasks/{task_id}/cancel` | required | Query param `terminate` (bool, default `false`) | `200 {"ok": true}`. Calls `celery_app.control.revoke(task_id, terminate=terminate)`. `terminate=false` only prevents a not-yet-started task from starting; `terminate=true` also kills it if already running. Does not check that `task_id` exists in celery-manager's own storage. |
| `POST` | `/api/tasks/{task_id}/retry` | required | — | `200 {"new_task_id": str}`. Looks up the original run's stored `args`/`kwargs` and re-dispatches them as a brand-new task (a new `task_id`, not a retry of the original in Celery's own sense). Writes an `AuditLog` row (`action="retry"`, `target_type="task"`, `target_id=task_id`, `details={"new_task_id": ...}`). `404`-equivalent: raises `ValueError` if no run is found for `task_id` — currently **unhandled** at the route level, so this surfaces as a `500`, not a clean `404`. |
| `POST` | `/api/tasks/retry-bulk` | required | `{"task_ids": [str, ...]}` | `200 {"new_task_ids": [str, ...]}`. Retries each id via the same logic as the single-retry endpoint (one `AuditLog` row per task), in list order. Same unhandled-`ValueError`-on-missing-id caveat as above — one missing `task_id` anywhere in the list fails the whole batch as a `500`, including entries already retried before it. |

## Schedules

| Method | Path | Auth | Request | Response |
|---|---|---|---|---|
| `GET` | `/api/schedules/{name}/occurrences` | required | — | `200` — list of `{"target_time": datetime, "action": "skip"\|"cancel"\|null, "consumed": bool}`, one entry per of the next 10 computed occurrences of the periodic schedule named `name` (from `celery_app.conf.beat_schedule`), in chronological order. `action`/`consumed` reflect any matching unconsumed `ScheduleOverride`, or `null`/`false` if none. Returns `[]` if `name` isn't a known schedule (rather than a `404`). |
| `POST` | `/api/schedules/{name}/occurrences/pause` | required | `{"target_time": datetime, "action": "skip"\|"cancel"}` (any other `action` value is a `422`) | `200 {"id": int, "action": str, "target_time": datetime}`. Records (or updates) an override for the occurrence closest to `target_time`. |

### Occurrence-matching nuances worth knowing

`GET .../occurrences` recomputes the schedule's next 10 run times **relative
to "now" on every call** rather than reading them from storage — so a
`target_time` returned a minute ago will not be byte-identical to the
"same" occurrence's `target_time` in a fresh call. To keep a paused
occurrence showing as paused despite that drift, matching between computed
occurrences and stored `ScheduleOverride` rows is done by proximity —
within `eta_tolerance_seconds` (from `CeleryManagerConfig`, default 60) —
not exact equality, using the closest override within the window rather
than the first one found.

This required two real fix rounds during implementation (see
`_find_within_tolerance` and `list_upcoming_with_overrides` in
`src/celery_manager/control/schedules.py`):

1. **Tolerance-window matching instead of exact equality** — the initial
   version matched `target_time` by exact equality, which meant a paused
   occurrence stopped showing as paused after even a few seconds, since the
   recomputed timestamp had drifted from the one originally sent to `POST
   .../pause`.
2. **Claim-based matching to prevent double-pause display** — on schedules
   whose interval is shorter than `2 * eta_tolerance_seconds`, a single
   override could legitimately fall within the tolerance window of *two*
   adjacent occurrences at once. `list_upcoming_with_overrides` now matches
   occurrences against the override pool one at a time in chronological
   order, removing ("claiming") each matched override from the pool before
   matching the next occurrence — so the same override is never reported
   against two rows.

`POST .../pause` has a matching idempotency behavior on the write side:
calling it again with a `target_time` within `eta_tolerance_seconds` of an
existing *unconsumed* override for the same schedule updates that row's
`action` and `target_time` in place (most recent request wins) instead of
inserting a second row — this is what keeps the read side from ever having
two overlapping, ambiguous rows for what a user would consider the same
occurrence (e.g. re-deciding the action after a page reload).

`action` accepts only `"skip"` and `"cancel"`. Anything else — including
`"reschedule"` — is rejected with a `422`. The `ScheduleOverride` table's
`action` column and its `reschedule_to` column still permit a reschedule
value at the schema level, but no reschedule-to-a-new-time behavior is
implemented anywhere: the decorator acts on `skip`/`cancel` only (see
[the decorator page](decorator.md)). The endpoint used to accept and store
`"reschedule"`, which then displayed in the dashboard as a paused occurrence
while doing nothing at all — rejecting it at the boundary is the honest
behavior until the feature actually exists.

## Audit log

| Method | Path | Auth | Request | Response |
|---|---|---|---|---|
| `GET` | `/api/audit` | required | Query param `limit` (int, default `50`) | `200` — list of `{"username", "action", "target_type", "target_id", "details", "created_at"}`, newest first (ordered by internal row id descending). `details` is a JSON-encoded string or `null`. |

Audit rows are written server-side whenever a control action is taken on a
user's behalf — currently just task retry and bulk retry (`action="retry"`,
`target_type="task"`), via `celery_manager.control.audit.record`. There is
no endpoint to write an audit entry directly; entries are always a
side-effect of another action.

## Live updates (SSE)

| Method | Path | Auth | Response |
|---|---|---|---|
| `GET` | `/api/stream` | **none** | `text/event-stream`. Each event is `data: {"task_id": str, "type": str}\n\n` (default `message` event name, no custom `event:` field), one line per Celery task-lifecycle event forwarded from the events listener (`task-sent`, `task-received`, `task-started`, `task-succeeded`, `task-failed`, `task-retried`, `task-revoked`) plus any other event types the listener chooses to publish. Connection stays open indefinitely; the client (dashboard) reconnects with the browser's native `EventSource` retry behavior. |

`/api/stream` is notably **not** behind `get_current_user` like every other
endpoint on this page — it has no auth dependency in the route definition.
The payload itself only carries a task id and event type (no task
name/args/output), so the practical exposure is limited, but this is worth
knowing if you're deploying somewhere the endpoint is reachable by
unauthenticated clients.

The dashboard's task list subscribes to this stream and refetches
`/api/tasks` on every event rather than applying the event to its local
state directly — see [Dashboard](dashboard.md).
